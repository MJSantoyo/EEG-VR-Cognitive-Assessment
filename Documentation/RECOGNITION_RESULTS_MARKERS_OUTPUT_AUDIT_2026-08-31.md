### 2. Root cause

**The delayed word was being written to a label in a different room, on a canvas that was switched off.**

`ExperimentUIController.SetWordDisplay(word)` wrote to exactly one field, `m_AreaAWord` →
`Txt_WordDisplay` on `UI_A_Canvas`, a child of the Area A panel.
`ShowArea(ExperimentArea.AreaC)` sets `m_AreaAPanel` inactive. Area A sits at world origin and
Area C at x = 200 m.

So during delayed recognition, `RunRecognitionItem` set the correct string on a **deactivated
GameObject 200 m behind the participant**. Nothing about the protocol, the item sequence, the
classification, the pacing or the logging was wrong — which is exactly why the instruction, the
narration and both response buttons all worked, and why the CSV recorded delayed items normally.

It was none of the other candidates considered: the reference was not wrong, the text was not
cleared after assignment, no canvas was in front of another, z / scale / parent were all correct,
`ClearWordDisplay` ordering was correct, and the response panel never touches the label.

**Why a second label rather than reusing the Area A one:** each area owns a world-space canvas
standing in its own physical room, and only one is active at a time. One label physically cannot
serve both. This is the same idiom the project already uses for the warning banner (`SetWarning`
writes four labels) and Recenter (four buttons). It is not two stimuli — the inactive one renders
nothing.

### 4. New display path

```
RunRecognitionItem → m_UI.SetWordDisplay(item.word)
       → SetText(m_AreaAWord)   ← inactive in Area C, renders nothing
       → SetText(m_AreaCWord)   ← Txt_WordDisplay_C, UI_C_Canvas, ACTIVE, in front of participant
→ Arm() → response → ClearWordDisplay() clears both → next item
→ phase end → ClearWordDisplay() → FinishAreaC → ClearWordDisplay() → SetResults(...)
```

The immediate phase is byte-for-byte unchanged: it still runs in Area A, where `m_AreaAWord` is
the active label and `m_AreaCWord` is the inactive one.

### 5. Exact UI object used

`Txt_WordDisplay_C` — `TextMeshProUGUI`, child of `UI_C_Canvas`, bound to
`ExperimentUIController.m_AreaCWord`.

- anchored position `(0, +165)`, size `1520 × 200`, 130 pt, colour `(1.00, 0.93, 0.50)` —
  identical type and colour to the Area A label
- `+165` is derived, not arbitrary: Area A's canvas is centred at 1.65 m with the word at +60 px,
  which at 0.00095 m/px is **1.707 m**; the Area C canvas is centred at 1.55 m, so
  `(1.707 − 1.55) / 0.00095 = 165`. The self test measures this and reports **0 mm** difference in
  world height and 130 pt vs 130 pt.
- Both canvases sit 2.1 m from their spawn at the same scale, so the immediate and delayed
  stimuli subtend the **same visual angle at the same eye height**. The two halves of one
  recognition measure should not differ in legibility.
- Clears the response pair (world y 0.95) by **0.76 m** — the same separation Area A already
  required.
- Named `Txt_WordDisplay_C`, not `Txt_WordDisplay`, so the existing
  `FindInSceneIncludingInactive("Txt_WordDisplay")` Area A zone check stays unambiguous.

It shares the vertical band the results block occupies. That is safe and asserted:
`RunRecognitionPhase` clears the word before Area C ever writes a summary, and `FinishAreaC` now
clears it again as a guard for every other route into the results screen.

**Transport facts that apply to every row below.** `EventLogger.Log` builds one `ExperimentEvent`
and publishes it synchronously to every `IEventSink` on the `EventLogger` GameObject:
`CsvEventSink`, `UnityConsoleEventSink`, `LslMarkerSink`. So **every event listed is emitted as an
LSL marker** when the outlet is Active. Timestamp source is uniform: `timestamp_absolute` and
`timestamp_relative` from `SessionClock` (monotonic `Stopwatch` anchored once to `DateTime.Now`),
`elapsed_trial_time` from the run `IntervalTimer`, and `lsl_timestamp` from `LslClock.Now()` =
liblsl `local_clock()` — stamped inside `Log`, on every row, never substituted from another clock.

`diff`, `word_index`, `word`, `phase` (from `recallPhase`, **not** `recognitionPhase`), `chair`,
`correct`, `rt_ms`, and `seed` on SESSION_START. Everything else in the payload column below
reaches the **CSV only**.

### NOT IMPLEMENTED

- **No dedicated "recognition phase transition" marker beyond the START/END pair.** There is no
  per-item block or sub-block marker.
- **No `RECOGNITION_ITEM_OFFSET`.** `WORD_OFFSET` exists for encoding only; a recognition word's
  removal is not separately marked — its offset is implicit in the response/timeout event.
- **No experiment-completion marker distinct from `SESSION_END` / `RUN_FINALIZED` /
  `SESSION_SUMMARY`.** Those three cover it; there is no separate `EXPERIMENT_COMPLETE`.
- **No recognition fields in any LSL marker payload.** `recognition_outcome`,
  `recognition_item_class`, `recognition_phase`, `recognition_item_id`,
  `recognition_presentation_order` and `recognition_response` reach the CSV only. `BuildMarker`
  reads `recallPhase`, which is empty for recognition rows, so recognition markers carry **no phase
  token at all** — an immediate and a delayed marker for the same word are indistinguishable in the
  marker stream alone. Joining on `lsl_timestamp` against the CSV is currently required to classify
  a recognition epoch. **Reported, not changed — the marker schema is locked.**

### Value-vocabulary observation (documentation vs. emitted values)

`ExperimentEvent.recognitionOutcome`'s doc comment states *"HIT, MISS, CORRECT_REJECTION,
FALSE_ALARM or NO_RESPONSE"*, but the code writes `enumValue.ToString().ToUpperInvariant()`, which
has no underscores. Live CSVs on this machine confirm the emitted vocabulary is:

- outcome: `HIT`, `MISS`, `CORRECTREJECTION`, `FALSEALARM`, `NORESPONSE`
- response: `SEENBEFORE`, `NOTSEENBEFORE`, `NONE`
- phase: `IMMEDIATE`, `DELAYED`

The data is self-consistent and analysable; only the comment is wrong. **Not changed — the CSV
schema is locked, and altering these strings would break every existing file.**

### Which are legacy FreeRecall

The last two rows. In Recognition mode `RunRecall` never executes, so `m_Result.immediateRecall`
and `m_Result.delayedRecall` stay `null`, `DescribeRecallStatus(null)` returns
`"no recording / not scored"`, and `RecallStatusLabel` maps that to `LocKeys.NotAvailable`.

**The participant currently sees, at the end of a Recognition run:**

> Immediate verbal recall: **Not available**
> Delayed verbal recall: **Not available**

Also legacy but not on screen: `RecallScore` (never populated — no transcription provider), and
`TrialResult.BuildSummaryText` (dead code, no longer called).

### Does it have access to Recognition Hit/Miss/CR/FA totals?

**No.** Not on the screen, and not in the object it reads. `SessionResults` contains no recognition
field of any kind. The only route to those numbers today is
`m_ExperimentManager.immediateRecognitionItems` / `delayedRecognitionItems`, which `SessionResults`
cannot see.

### Are Immediate and Delayed Recognition results aggregated?

**Only ephemerally.** `RecognitionSequence.Summarise(store)` computes the five counts and
immediately formats them into a string for the `*_RECOGNITION_END` event's `notes`. No typed counts
survive the call. There is no `SessionResults.immediateHits`, no `recognitionSummary` struct,
nothing.

### Do those values exist only per item?

**Yes, as typed data.** The per-item record is complete and correct — `RecognitionItem.outcome` is
derived, so it can never contradict the class and response it summarises, and every item is written
to the CSV. Session-level recognition totals exist **only** as (a) that one formatted `notes`
string, and (b) whatever an analyst recomputes from the CSV.

| Name | Where | Why misleading |

### Minimum data needed later to display Recognition results correctly

Stated as a requirement only — **nothing implemented**, and note that how a recognition result
should be *presented to a participant* is a methodological decision, not an engineering one.

1. **Typed per-phase counts on `SessionResults`**, populated from the existing
   `m_ImmediateRecognitionItems` / `m_DelayedRecognitionItems`: hits, misses, correct rejections,
   false alarms, no-response, item count, target count, lure count — per phase, kept separate. All
   five are already derivable from data that exists; nothing new needs measuring.
2. **A protocol-aware branch in `BuildParticipantRunSummary`**, so Recognition mode shows
   recognition rows and FreeRecall mode shows recall rows — rather than one screen showing the
   other protocol's empty fields.
3. **New localization keys** for the recognition rows in EN/ES/JA. The existing
   `StatImmediateRecall` / `StatDelayedRecall` keys must not be reused: their strings say "verbal
   recall" and mean something else.
4. **A decision on what the participant should see at all.** The chair task shows "N / M correct";
   whether a memory result should be shown to a participant — and in what form — is a protocol
   question. The current screen deliberately withholds per-trial chair correctness for exactly this
   reason.
5. Optionally, recognition columns in `session_summary_*.csv`. That file is derived and
   regenerable, so extending it costs nothing — but it is still a schema change and needs explicit
   sign-off.

# ADDENDUM — 2026-09-02 · ANALYSIS TIME-BASE CLOCK-DOMAIN FIX

The audit above and the 2026-09-01 addendum are preserved as written. This entry records a
timestamp defect found after them, which affects how §3/§4 of the audit should be read.

## What was wrong

`lsl_timestamp_analysis` — the column §7 row 1 of the audit describes as the base for cutting
epochs — could be written in the **sender's** clock domain instead of this machine's.

Observed in `S_20260902_131219_r01_27eda8`: analysis ≈ 1 340 672 s while the event CSV and
`lsl_timestamp_local_raw` were ≈ 97 872 s, with the analysis column advancing at **416.7 Hz**
against an advertised 250 Hz. Every Recognition epoch cut from that column was empty or wrong.

**Root cause.** `AuraLslReceiver.RefreshTimeCorrection(initial: true)` has a 2 s timeout. When it
fails, `m_TimeCorrection` stays `0`, so `localRaw = remote + 0` — the remote domain. Those samples
seeded `EegAnalysisTimebase`, which anchors on its first sample and integrates forward with a
steering correction clamped to ±0.4 sample intervals. When the correction later arrived the raw
column snapped into the local domain; the grid could not follow, saturated its clamp on ~27.6 % of
samples, and free-ran at `nominal − 0.4 × nominal = 2.4 ms` = 416.7 Hz for the whole recording —
smooth, strictly monotonic and entirely fictional. Closing a 1.24 × 10⁶ s error at 1.6 ms/sample
needs ≈ 7.8 × 10⁸ samples (~36 days).

## Effect on the earlier audit

- **§7 row 1 and §4 still stand for `S_20260901_184525_r01_88cb0d`.** That session's first
  `time_correction` succeeded, so its analysis column was always in the local domain. The HARBOR
  epoch reported in the 2026-09-01 validation remains valid.
- **`lsl_timestamp_analysis` must no longer be trusted unconditionally.** The audit's statement
  that the file header "names this as the column to cut epochs with" is still the intent, but a
  recorded file can now be *checked* rather than assumed — see the integrity guard below.
- **`lsl_timestamp_local_raw` was correct in both sessions**, which is why the broken recording is
  fully recoverable offline.

## Time-base contract, now enforced

| Column | Domain | Guarantees |
|---|---|---|
| `lsl_timestamp_remote_raw` | sender's clock | as received; provenance only; never used for alignment |
| `lsl_timestamp_local_raw` | this machine's LSL clock — same as `events_*.csv` `lsl_timestamp` | `remote + time_correction`; may be non-monotonic (chunk-anchor jitter) |
| `lsl_timestamp_analysis` | **must equal the local domain** | monotonic by construction; mean spacing ≈ 1/nominal; directly comparable with event timestamps; must never drift into the remote domain |

## Fix

- `EegAnalysisTimebase` re-anchors when the grid leaves the raw local clock by more than
  `max(5 s, 1000 × sample interval)`, exposes `reanchorCount` / `isTracking` /
  `totalSaturatedRuns`, and `Reset()` now clears that history.
- `AuraLslReceiver` calls `InvalidateAnchor(...)` when `time_correction` moves by more than the
  grid can steer, and logs it as a warning.
- Thresholds are measured, not chosen: healthy grid-vs-raw drift is 0.205 s / 0.314 s across the
  two sessions and the longest healthy saturation run is 86 samples, so the bounds sit an order of
  magnitude above the healthy envelope and five orders below the failure.
